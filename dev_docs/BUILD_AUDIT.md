## Summary

The codegen chain has one clean, enforced spine — `export_and_build_types.py` is
wired into all three entry scripts and fails loud — but almost everything around it
is **generate-once, commit, and hope**. The dominant theme is exactly the one this
audit was chartered to find: **committed artifacts that no wired step regenerates,
so they drift from source silently**, plus a `.gitignore` that actively *hides* that
drift by claiming files are ignored when they are in fact tracked.

Highest-priority item: **H1 — `sandbox_host.exe` is committed to git**, in direct
contradiction of both `.gitignore:2` and CLAUDE.md's "The binary is not committed to
git." This is the process-isolation boundary binary. Because git ignore rules do not
apply to already-tracked files, the gitignore entry gives false assurance while a
368 KB compiled blob — which can be stale relative to `src/*.cpp`, or tampered — ships
in the tree with no verifiable provenance. **Security-adjacent.**

Second: **H2 — `gen_constants.py` is in no build, start, or runtime chain**, yet one
of its outputs is committed and 16 backend modules (including the SQLModel tables that
feed the OpenAPI export) import it. A change to `config/constants.yaml` or
`config/emulators/*.toml` silently diverges the committed `constants_generated.py`,
and the frontend's `constants.ts` (gitignored, untracked → **absent on a fresh clone**)
is never regenerated by `build.bat`.

There is **no CI, pre-commit hook, or husky config anywhere** (`.github/` does not
exist; TECH.md lists CI/CD as planned, P7), so *every* "must re-run" rule below is
doc-only or tribal.

No Critical (data-loss / RCE / auth-bypass) findings. Findings are static-analysis
conclusions; no generator or build was executed.

Counts: **Critical 0 · High 2 · Medium 3 · Low/DeadCode/TechDebt 4.**

## HIGH

### H1 — `sandbox_host.exe` is committed to git despite gitignore + CLAUDE.md saying it is not  ⚠️ SECURITY-ADJACENT
- **Category:** drift / provenance on the isolation boundary
- **Where:** tracked at `backend/service/utils/platform/windows/sandbox/sandbox_host.exe`
  (368,640 bytes; last touched in commits `c96b1ce`, `8feca1c`). Contradicts
  `.gitignore:2` and CLAUDE.md ("build.bat does this automatically via MSYS2 … The
  binary is not committed to git.").
- **What:** the file is in the index. `git check-ignore` reports it "not-ignored"
  **because ignore rules never apply to already-tracked paths** — so the gitignore
  line is inert and misleading. The intended model (gitignore the binary, rebuild it
  from `src/` via `build.sh` on every `build.bat`) is silently defeated: the committed
  copy shadows the rebuild intent, and a reviewer trusting the gitignore/CLAUDE.md
  statement would believe no binary is checked in.
- **Why it matters:** this is the Job-Objects/container isolation host. A committed
  binary can be (a) **stale** relative to `src/*.cpp` — a security fix in
  `container.cpp`/`job.cpp`/`watchdog.cpp` would not take effect for anyone who runs
  from the tracked exe without rebuilding; (b) **unverifiable** — there is no way to
  confirm the committed blob was built from the committed source; (c) a supply-chain
  surface — a modified isolation binary would travel with the repo. `build.bat:180`
  *does* rebuild over it locally, which then shows the "ignored" file as modified in
  `git status`, further muddying whether the committed copy is authoritative.
- **Direction (flag only):** decide one model and make it true — either genuinely
  untrack it (`git rm --cached`, keep the gitignore, rely on `build.sh`/pre-built
  drop-in) so the boundary binary is always built from source, or commit it
  deliberately with a documented, reproducible build + checksum and drop the false
  gitignore line. The current half-state is the worst of both.

### H2 — `gen_constants.py` runs in no chain; its committed output drifts from source and its frontend output is absent on clone
- **Category:** silent drift between generated artifact and source / undocumented ordering
- **Where:** `scripts/gen_constants.py` (reads `config/constants.yaml` +
  `config/emulators/*.toml`; writes `backend/constants_generated.py` and
  `frontend/src/generated/constants.ts`). No caller in `build.bat`, `start.bat`,
  `start.sh`, `main.py`, or `backend/core/**` — the only documentation of "must run
  it" is the script's own docstring.
- **What:**
  - `backend/constants_generated.py` is **committed** (`.gitignore:120` lists it, but
    it was tracked before the rule, so the rule is inert — same trap as H1). Editing
    `constants.yaml`, or adding/removing an emulator TOML under `config/emulators/`,
    silently diverges the committed file until someone remembers the manual
    `python scripts/gen_constants.py`.
  - `frontend/src/generated/constants.ts` is **gitignored and untracked** → **absent
    on a fresh checkout**. It is imported by 16+ frontend modules (e.g.
    `components/Tags/swatches.ts`, `pages/Emulators/ProfilesTab.tsx`,
    `pages/Environments/*`). `build.bat`'s frontend `npm run build` never regenerates
    it, so a clean-clone build has no wired step that produces it.
  - **Undocumented ordering:** 16 backend modules import `constants_generated`,
    including the SQLModel tables (`models/platform.py`, `library.py`, `tag.py`,
    `profile.py`, `launch_history.py`) that `export_and_build_types.py` pulls in via
    `backend.api.routes.ROUTERS`. So `gen_constants.py` must run **before**
    `export_and_build_types.py` for a constants change to reach `openapi.json` →
    `types.ts`. `build.bat:129` runs the second but never the first — the ordering is
    real, load-bearing, and unenforced.
- **Why it matters:** this is the canonical "generated artifact diverges from source
  without anyone noticing" risk. The Python half drifts committed; the TS half is
  missing on clone; and the two halves can diverge from each other and from the
  OpenAPI spec because nothing sequences or regenerates them.
- **Direction (flag only):** flag that `gen_constants.py` has no home in any chain and
  that its ordering relative to `export_and_build_types.py` is undocumented. (Wiring /
  consolidation intentionally out of scope per brief.)

## MEDIUM

### M1 — Two divergent builders for the same isolation binary; the MSVC one is orphaned  ⚠️ SECURITY-ADJACENT
- **Category:** duplicated build recipe (drift risk) on the isolation boundary
- **Where:** `scripts/build_sandbox_host.bat` (MSVC `cl.exe`) vs
  `backend/service/utils/platform/windows/sandbox/build.sh` (MSYS2 `g++`). Same five
  sources (`main/container/job/watchdog/event.cpp`), **different toolchains and link
  sets**: the `.bat` links `user32.lib userenv.lib ole32.lib advapi32.lib kernel32.lib
  shlwapi.lib` (`build_sandbox_host.bat:195`); `build.sh` links
  `-luserenv -lole32 -ladvapi32 -lkernel32` (`build.sh:27-30`) — **no `user32` or
  `shlwapi`**, and different warning/opt flags (`/W3 /O2` vs `-Wall -Wextra -O2`).
- **What:** only `build.sh` is wired into `build.bat:180`. `build_sandbox_host.bat` is
  never invoked by any script (searched the whole tree — self-reference only), so it
  is a manual/dev-only alternative that can bit-rot and, if used, produces a *different*
  binary from the pipeline's. Two recipes for one security-critical artifact that must
  behave identically but are not guaranteed to.
- **Why it matters:** an isolation binary built two ways with different linked Win32
  surfaces is a divergence hazard exactly on the boundary where behavior must be exact.
  Whichever a given machine happens to run is non-obvious.
- **Direction (flag only):** note the divergence and the orphan status; pick a single
  canonical builder or keep them provably in lockstep. (No consolidation proposed here.)

### M2 — sandbox_checker capability-probe `.exe`s are committed and never rebuilt by the pipeline  ⚠️ SECURITY-ADJACENT
- **Category:** committed binaries drift from source
- **Where:** `backend/service/utils/platform/windows/sandbox_checker/src/test_sdl2_d3d11.exe`,
  `test_sdl2_opengl.exe`, `test_qt_qpa.exe` — all **tracked** (not in `.gitignore` at
  all), built by `build_tests.sh` in the same dir.
- **What:** `build_tests.sh` is invoked by **nothing** in the build chain.
  `build.bat:234-240` merely checks the exes exist and copies them to `dist/`; it never
  builds them. So the committed probe binaries can drift from their `.cpp` sources
  indefinitely, and `checker.py:89` only surfaces a runtime "not built — run
  build_tests.sh" message if an exe is missing — never if it is stale.
- **Why it matters:** these probes decide whether the container has working GPU/display
  paths (D3D11, OpenGL, Qt QPA) — a sandbox-capability signal. Stale probes give wrong
  capability answers. It is also the mirror-image asymmetry to H1: here binaries are
  *committed and never rebuilt*; there the binary is *rebuilt but "ignored"* — neither
  path guarantees exe-matches-source.
- **Direction (flag only):** flag that three security-adjacent binaries are committed
  with no regeneration in any chain and no staleness detection.

### M3 — `export_and_build_types.py` ROUTERS/main.py parity is enforced only by a CLAUDE.md gotcha
- **Category:** enforcement gap on a known recurring bug
- **Where:** `scripts/export_and_build_types.py:21-33` builds a throwaway app from
  `backend.api.routes.ROUTERS` only.
- **What:** CLAUDE.md already documents this as "a recurring bug" — a router mounted in
  `main.py` but absent from the `ROUTERS` list silently yields a stale spec and broken
  types. The script itself fails loud on export/`npm` errors (good), but it cannot
  detect a *missing* router — the failure mode is a quiet, correct-looking-but-partial
  spec. There is no automated parity check; the safeguard is the doc note plus reviewer
  memory. Its outputs (`shared/openapi.json`, `shared/types.ts`) are untracked, so any
  environment that does not run the script (only `build.bat`/`start.*` do) has no spec
  at all.
- **Why it matters:** it is the one part of the chain that *is* wired, but its most
  dangerous failure (router drift) is fail-silent and enforced tribally.
- **Direction (flag only):** note the absence of any mechanical ROUTERS-vs-mounted
  parity check.

## LOW / DEAD CODE / TECH DEBT

### L1 — `.gitignore` references a generator (`merge_emulators.py`) that does not exist
- **Where:** `.gitignore:100-102` — "Merged config outputs (generated by
  merge_emulators.py)" for `config/86box-profiles.toml` and `config/emulators.toml`.
- **What:** no `merge_emulators.py` exists anywhere in the tree, and neither merged
  file is present or produced. The runtime now reads the **directory** form directly:
  `emulator_catalog.py:22-50` loads `config/emulators/*.toml`, and
  `get_86box_profile` (`emulator_catalog.py:105-117`) reads
  `library/system/templates/86box/86box-profiles.toml` **or** falls back to the
  per-file dir. The gitignore comment is a dead pointer to a removed generation step —
  a doc-drift trap for anyone reasoning about how those files are produced.
- **Direction (flag only):** stale reference; the merge step is gone.

### L2 — `gen_icon.py` is orphaned and does not produce the file the build actually consumes
- **Where:** `scripts/gen_icon.py` writes a 16×16 placeholder `assets/peach1up.png`;
  `peach1up.spec:95` consumes `assets/peach1up.ico` ("convert from png before
  building"). Both `.png` and `.ico` are committed; **no script converts png→ico.**
- **What:** the generator's output is not the build input. `gen_icon.py` is effectively
  dead (placeholder only, invoked by nothing but a README line), and the real build
  asset (`.ico`) has no generator and an undocumented manual conversion prerequisite.
  Low impact only because the `.ico` is committed, so PyInstaller does not fail.
- **Direction (flag only):** orphan script + undocumented manual conversion step.

### L3 — `hash_index.json` is committed but not reproducible or verifiable from the repo
- **Where:** `backend/service/utils/smart_media_detector/hashing/build_index.py` →
  committed `hash_index.json`.
- **What:** rebuilding requires external No-Intro/Redump DAT files (`--dats <dir>`,
  required) that are not in the tree, so the committed index cannot be regenerated or
  verified from source alone — there is no way to detect a stale or hand-edited index.
  Default (non-`--rebuild`) mode is **incremental and never removes** entries
  (`build_index.py:59,84`), so retired DAT entries persist across rebuilds. The script
  itself fails loud on a missing `--dats` dir, and `hash_lookup.py:102` fails
  loud/logged if the index is missing — so failure behavior is sound; the gap is
  provenance/verifiability, not fail-silence.
- **Direction (flag only):** curated data bundle with no in-repo provenance path.

### L4 — No enforcement layer exists for any "must re-run" rule
- **Where:** repo-wide. No `.github/` (no CI), no `.pre-commit-config.yaml`, no
  `.husky/`. TECH.md lists CI/CD as planned (P7).
- **What:** every regeneration/rebuild rule in this audit is doc-only or tribal. The
  only *mechanical* guards are (a) the entry scripts' own `exit 1` on failure and
  (b) `build.bat`'s existence checks for pre-built binaries. Nothing checks that a
  committed generated artifact matches its source, that `ROUTERS` matches `main.py`,
  or that a `.cpp` change was followed by a binary rebuild.
- **Direction (flag only):** the enforcement surface is empty; this is the umbrella
  reason the H1/H2/M1/M2 drift risks can go unnoticed.

## Areas reviewed and found clean (no finding)

- **`export_and_build_types.py` wiring & failure behavior:** correctly invoked in all
  three entry scripts (`build.bat:129`, `start.bat:110`, `start.sh:79`), runs before
  the docs build that depends on `openapi.json` (`build.bat:125-135`), and fails loud
  with `sys.exit(1)` on both spec-export failure and `npm run generate:api` non-zero.
  Its only gap is the ROUTERS-parity blind spot (M3), not its plumbing.
- **`build.sh` (sandbox) failure behavior:** `set -euo pipefail` with an explicit
  source-list; a `g++` non-zero aborts the whole `build.bat` (`build.bat:180-184`), and
  the no-MSYS2 branch fails loud if a pre-built exe is also missing
  (`build.bat:186-194`). Fail-loud contract is sound — the problem (H1) is the tracked
  binary shadowing it, not the script.
- **`build_sandbox_host.bat` failure behavior:** validates each of the five sources
  (`:45-69`), locates the toolchain via `vswhere`/`vcvarsall` with actionable errors,
  cleans the obj dir, and explicitly does **not** update the exe on a failed compile
  ("sandbox_host.exe was NOT updated", `:204-208`). Fail-loud is correct; the issue
  (M1) is divergence/orphan status, not silent staleness.
- **`build.bat` bundle hygiene:** strips machine-specific keys and deletes `paths.yaml`
  from the shipped `settings.yaml` (`:247-254`), and `peach1up.spec:63-74` filters
  `__pycache__`, tests, and `roms/bios/saves/vms` out of `datas`. No secret or
  machine-path leakage into the bundle was found on this pass.
- **`build_index.py` / `build_tests.sh` internal fail-loud:** both check their required
  inputs/tools up front and exit non-zero with actionable messages
  (`build_index.py:55-57`, `build_tests.sh:8-20`). Their finding (M2/L3) is drift and
  not being wired in — not fail-silence within the script.
