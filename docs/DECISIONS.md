| 2026-05-19 | 86Box VM directory layout follows portable mode conventions  | 86Box resolves all paths in its config relative to the VM directory (CWD at launch). Fighting this by splitting config, disk images, and binaries across separate directory trees causes path resolution failures. The correct layout colocates all VM working files (86box.cfg, disk.vhd, nvr/, screenshots/, saves/) inside emulators/86box/vms/<slug>/. The installation ISO remains in library/os/ as read-only source media and is referenced by absolute path in the config. 86Box is launched with --vmpath pointing to emulators/86box/vms/ and CWD set to the VM subdirectory. This layout is compatible with 86Box Manager and follows how 86Box portable mode is designed to operate. |

| 2026-05-19 | Environments are a UI/UX abstraction over the 86Box VM directory layout | The Environment concept exists to give users a clean abstraction — name, era, hardware profile, installation media — without exposing the underlying filesystem structure. On disk, each environment maps directly to a subdirectory under emulators/86box/vms/<slug>/. Users never navigate file paths directly unless they use Advanced settings. The Environment record in the database points to the VM directory; Peach 1UP manages all file operations within it. |
| 2026-05-19 | Qt-based emulators require skip_memory_limit in Job Object | Qt's security initialisation (platform plugin startup) calls trigger STATUS_STACK_BUFFER_OVERRUN (0xC0000409 fast-fail) when JOB_OBJECT_LIMIT_PROCESS_MEMORY is applied to the process after creation via AssignProcessToJobObject. Confirmed on 86Box 5.3 (Qt 5.15.18) on Windows 11. Kill-on-close and CPU rate control are unaffected. skip_memory_limit = true set in emulator descriptor for 86Box, DuckStation, PCSX2. SDL2-based emulators (DOSBox-X, ScummVM, Flycast, xemu, Mesen, Project64) are not known to exhibit this behaviour and use skip_memory_limit = false. |
| 2026-05-17 | VirtualBox removed from emulator stack entirely | 86Box covers Win9x and XP with better accuracy and fits the portable emulator model. VirtualBox resists portable mode, requires a system service (VBoxSDS) that cannot be cleanly managed by the launcher, and is poorly suited for retro gaming use cases. All Win9x and XP launches now route to 86Box exclusively. Flycast (Dreamcast) and ScummVM (point-and-click adventures) added to the supported emulator stack. Supersedes "VirtualBox as default for Win95/98 and XP" (2026-05-03) and "Windows 7 support added to VirtualBox era mapping" (2026-05-07). |
| 2026-05-17 | Win9x default backend flipped from VirtualBox to 86Box | VirtualBox gives near-native CPU speed but poor compatibility for Win95/98 titles that require cycle-accurate hardware timing, specific chipset behaviour, or legacy peripheral emulation. 86Box provides full cycle-accurate hardware emulation (CPU, chipset, sound, video) and is the preservation standard for Win9x software. The accuracy tradeoff is acceptable: the titles users want to run via Peach 1UP are preservation targets, not performance benchmarks. VirtualBox remains available as a user override but is no longer the default provisioning path for win95 and win98 environments. Supersedes "VirtualBox as default for Win95/98" (2026-05-03) and "86Box as opt-in accuracy mode only" (2026-05-03). |
| 2026-05-17 | Emulator path model: bundled, catalog-detected, and settings.yaml override | Emulator binary path resolution follows three tiers in priority order. (1) User override: absolute path stored in settings.yaml, set via the Emulators or Settings page in the UI — never accepted from request input. (2) Bundled: portable emulators ship inside emulators/{slug}/ under the project root; presence detected by checking the known project-relative path on startup. (3) Catalog-detected: system-installed emulators (VirtualBox, DuckStation, Project64) are located via known installation paths declared in emulators.yaml — no registry scanning. No emulator binary path is ever accepted from request input at launch time; this rule has no exceptions. |
| 2026-05-17 | Platform image path allowlist removed; images may reside anywhere on the host | The runtime check that required base_image_path and working_image_path to reside under a configured base directory (OS_PATH or LIBRARY_PATH) was intentionally removed. Hobbyist users routinely store large disk images on secondary drives, external volumes, or NAS shares that fall outside the configured library directories. Requiring those paths to be moved or reconfigured creates friction with no practical security benefit for the local single-household use case. The security tradeoff is explicit: path traversal protection for image paths now relies on the OS filesystem permissions and user trust model rather than application-level allowlist validation. Tracked as a known security gap in SECURITY.md. |
| 2026-05-14 | NSSM service runs as LocalSystem by default | For production hardening, lock down with nssm set Peach1UP ObjectName "NT AUTHORITY\NetworkService" or a dedicated service account. Tracked as a pre-release hardening item. |
| 2026-05-14 | Platforms renamed to Environments; Platforms page merged into Emulators page | The Platforms page was showing emulator binary status, which belongs on the Emulators page. Platforms as a concept is renamed to Environments — persistent managed workspaces for software requiring installation and accumulated OS state. The Environments page is a clean scaffold. Backend model classes and DB fields retain Platform naming until a dedicated migration is planned. |
| 2026-05-14 | Library items and Environments are distinct execution models | Library items follow a launch-play-cleanup cycle — emulator state torn down after every session, save data persisted externally to library/saves/{slug}/. Environments are persistent managed workspaces for software requiring installation, registry state, or long-term OS persistence. The distinction is not game vs tool — it is consumable vs persistent. Direct launch is the default; Environments are opt-in for content that genuinely requires a managed environment. |
| 2026-05-14 | Profiles scoped to emulators, not eras | Profiles are reusable launch configurations — CLI flags, scripts, ROM pack paths, mods, extensions — injected at run time. Scoped to a specific emulator because settings are emulator-specific. Duplicate button allows cloning across similar emulators. Profiles live under Emulators in the nav. Tags associate profiles with environments or content types instead of hard FK relationships. |
| 2026-05-14 | Tags system with pre-created system tags | Tags associate profiles with contexts — environments, hardware configs, content types. System tags pre-created at first run for emulators, eras, hardware configs (voodoo, mt32, soundblaster, adlib, ega, vga, svga), and content types (accuracy-mode, networking, mods, extensions). Users can create custom tags freely on top. System tags provide consistent vocabulary for search and filtering. |
| 2026-05-14 | Peach 1UP only manages processes it launches directly | Peach 1UP tracks, isolates, secures, and cleans up only processes launched via its own launch flow under Job Objects. Software launched externally — including emulator installers via ShellExecute — runs outside process tracking, Job Objects, and launch history. This is intentional. UI notes near Run Installer buttons clarify the installer runs independently and Peach 1UP detects the result when complete. |

| 2026-05-13 | peach_sandbox account isolation removed | The restricted local account approach provided filesystem ACL isolation but blocked audio access for all emulators, required the backend to run as Administrator, and added significant setup complexity for marginal security gain. Job Objects (CPU limits, memory limits, kill-on-close) provide the meaningful isolation and are independent of the account used. peach_sandbox removed entirely. | 2026-05-13 | Conf merge approach removed; inline -c args confirmed sufficient | A temp conf file approach (merging dosbox-x.conf with a generated autoexec block, written to C:\ProgramData\Peach1Up\temp) was introduced during P6 sandbox debugging. Root cause of all launch failures was peach_sandbox lacking ACL read access to emulator and media directories — not path formatting or conf parsing. Once ACL grants were automated in create_sandbox_user.ps1, inline -c imgmount args worked correctly without a temp file. dosbox_paths.py and all conf merge machinery removed. |
| 2026-05-13 | peach_sandbox requires explicit ACL grants on emulator and media directories | CreateProcessWithLogonW succeeds but the child process fails to read the emulator binary or media files if peach_sandbox lacks RX on those directories. Windows does not inherit the launching user's file access. ACL grants must be applied automatically in create_sandbox_user.ps1 after account creation, covering all configured emulator binary directories, IMAGES_PATH, and ROM_PATH from settings.yaml. Manual icacls grants are not acceptable as a setup step. |
| 2026-05-12 | Auth model finalised for P6.5 | Owner + sub-accounts with Argon2id PIN hashing, 4-attempt lockout, owner reset via settings, emergency recovery via scripts/setup_admin_user.py. Replaces the placeholder profile-switching concept from SECURITY.md. |
| 2026-05-07 | Windows emulator launches run under a dedicated low-privilege user | Running emulators as the same user as the Peach 1UP backend exposes the owner's home directory and profile data to compromised emulator code. A dedicated local account (`peach_sandbox`) with restricted ACLs limits damage: emulators can only read binaries and media paths explicitly granted to that account, not arbitrary user files. This is a defence-in-depth measure and a stepping stone toward stronger isolation (e.g. AppContainer). |
| 2026-05-07 | Job Objects required for Windows emulator launches where available | Job Objects provide reliable process-tree lifecycle management and CPU limits. All Windows emulator launches must be assigned to a Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and a sane default CPU cap. This guarantees that emulator trees are torn down if the backend exits and reduces the risk of thermal or power spikes. When assignment fails due to OS limitations, the launch is logged and treated as a weaker fallback. |
| 2026-05-07 | AppContainer and Win32 App Isolation deferred to a later phase (P8+) | AppContainer and emerging Win32 App Isolation features provide a stronger security boundary than a low-privilege user plus Job Objects, but require significant investment: installer-time provisioning, ACL management for container SIDs, and careful GPU/device access handling. They are tracked as a future enhancement after the low-privilege user and Job Object baseline is stable and well-tested on Windows 10/11. |
| 2026-05-07 | Windows Firewall COM network blocking removed | Firewall rule creation via Windows COM requires elevation, fails with E_ACCESSDENIED on standard installs, and is the wrong isolation primitive for this use case. Removed entirely. Network isolation is now emulator-native — DOSBox-X disables the NE2000 adapter, 86Box omits the network device from machine config, VirtualBox sets --nic1 null via VBoxManage. No elevation required. Controlled by enable_networking profile flag, default false. |
| 2026-05-07 | enable_networking added to profile model, default false | Users can enable networking per profile for software that requires it. When false the emulator launches with its network adapter disabled or absent. When true the emulator default is used. This gives users explicit control and keeps the default posture safe without requiring host OS firewall changes. |
| 2026-05-07 | Alembic removed in favour of SQLModel create_all() | Alembic adds migration overhead that is not justified while no real user data exists and the DB can be wiped freely.
