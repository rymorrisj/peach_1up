# Windows Sandboxing

Every emulator launch is wrapped in a Windows
[Job Object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), with
[AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)
layered on top where the emulator supports it.

## What the Job Object does

| Control | Effect | Waivable |
|---|---|---|
| Kill-on-close | Every emulator process in the job is terminated when the backend exits. No orphans | No, always applied |
| CPU cap | Threads are throttled past the per-era budget per scheduling interval, applied as `MaxRate` under `MIN_MAX_RATE` | `skip_cpu_limit` |
| Memory cap | Per-process cap so a runaway emulator cannot exhaust host RAM | `skip_memory_limit` |

**No emulator waives either cap today.** Every descriptor in `config/emulators/` sets both
flags to `false`, so all three controls are in force on every launch.

If the Job Object cannot be created, or the emulator cannot be assigned to it, **the launch
is aborted**. There is no fallback to an uncontained launch.

Emulators run under the current user account. A dedicated low-privilege account was tried
and removed: it blocked audio for every emulator, required the backend to run as
Administrator, and added significant setup complexity for marginal gain.

**What the Job Object does not do:** restrict filesystem access (that is AppContainer's job)
or block network access at the OS level (that is emulator-native, see
[Security Architecture](./security.mdx)).

## Resource caps

Per-era caps live in `config/eras.yaml`:

```yaml
dos:
  memory_limit_mb: 512
  cpu_limit_percent: 50
```

| Field | Sets |
|---|---|
| `memory_limit_mb` | Per-process memory cap in MB |
| `cpu_limit_percent` | CPU budget as a percentage of all logical processors per scheduling interval |
| `cpu_min_rate_percent` | Top-level, default `5`. The `MinRate` scheduling floor shared by every era |

### Hardcoded ceilings

Values are clamped once, when `eras.yaml` is loaded and cached, so every downstream reader
sees the clamped number with no per-call-site check.

| Ceiling | Value |
|---|---|
| `cpu_limit_percent` | 90 |
| `memory_limit_mb` | 75% of real total physical RAM, queried per process |

An over-ceiling value logs a warning and uses the ceiling for that run. It never raises: a
resource-tuning mistake should degrade loudly, not take startup down. There is no config key
or UI control for either ceiling; moving them requires a code change.

### Adjusting caps

Edit the era in `config/eras.yaml` and restart the backend. Changes apply on the next
launch. There is no settings field and no UI for these values.

**CPU notes**

- The cap spreads across all logical processors. On an 8-thread machine,
  `cpu_limit_percent: 50` allows the equivalent of 4 threads of CPU time per interval.
- `MIN_MAX_RATE` needs Windows 10 1607 (build 14393) or later. Below that, and on any
  `SetInformationJobObject` failure, the wrapper falls back to `HARD_CAP`.
- On `MIN_MAX_RATE`, a value at or below `cpu_min_rate_percent` is clamped up to that floor
  with a warning.
- `HARD_CAP` starves threads to zero CPU at interval end, which mutes the host WASAPI audio
  session. That is why `MIN_MAX_RATE` with a non-zero `MinRate` is the primary path.

**Memory notes**

- The cap is per-process, not per-job. Child processes each get it individually.
- Too low for a heavy era and the emulator crashes or fails to load large games. xemu needs
  the `xbox` cap above 2048 MB or it exits immediately with a paging file error.

## Launch sequence

```
launch suspended (CREATE_NEW_PROCESS_GROUP | CREATE_SUSPENDED)
  → create the Job Object, named with the launched process PID for per-launch uniqueness
  → apply limits
  → AssignProcessToJobObject
  → on error 5: kill the still-suspended process, relaunch with
    CREATE_BREAKAWAY_FROM_JOB, reassign
  → ResumeThread
```

Launching suspended means the emulator cannot execute before limits are in force. A process
that fails at any step is terminated while still suspended, never resumed.

For AppContainer-enabled emulators, process creation is delegated to `sandbox_host.exe`,
which handles `SECURITY_CAPABILITIES`, `CREATE_SUSPENDED | EXTENDED_STARTUPINFO_PRESENT`,
and `ResumeThread`. Its own Job Object applies the numeric limits before the process
resumes, so the Python-side job is created with `apply_limits=False` and exists only as a
teardown handle and for launch-history reporting. The resolved era numbers reach it through
`SandboxConfig`; without them it silently falls back to inert defaults.

Job Object and process lifecycle live in the standalone
[wincage](https://github.com/rymorrisj/wincage) package.

## Troubleshooting

**Emulator crashes immediately with no error.** The era memory cap is probably too low.
Raise `memory_limit_mb` in `eras.yaml` and restart.

**Job Object assignment fails with error 5 on Windows 11.** Windows 11 pre-assigns new child
processes to an OS-managed job, and a second assignment fails with access denied unless the
process was launched with `CREATE_BREAKAWAY_FROM_JOB`. The launcher retries automatically.
If the retry also fails (the process is inside a non-breakaway job set by a third-party tool
or debugger) the launch aborts and the error surfaces to the user.

## DOSBox-X specifics

`write_launch_conf()` builds a complete `dosbox-x.conf` per launch: it takes the bundled
base template, strips any `[autoexec]` section, and appends a generated one with drive mounts
followed by profile-level and item-level launch commands. The result goes into a private
per-launch temp directory, removed after the process exits.

The command line passes `-noconfig` (so DOSBox-X ignores any user config), `-conf <path>`,
and an optional `-set ne2000=false` when networking is disabled for the profile.

Inside the generated `[autoexec]` block, paths reach `MOUNT` and `IMGMOUNT` as raw absolute
Windows paths, double-quoted only when they contain whitespace. Forward slashes and 8.3
short-path conversion are not used: the DOSBox-X autoexec tokeniser reads a forward slash as
a DOS switch character and truncates the argument.

Before the per-launch temp directory existed, all launches wrote their conf to one shared
location, which a concurrent second launch could overwrite mid-read.
